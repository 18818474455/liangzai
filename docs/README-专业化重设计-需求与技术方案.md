## 1. 用户明确提出的问题

1. 当前 README 审美不够专业。
2. 页面缺少真正的设计，不应只是 Markdown 文案、徽章和截图堆叠。
3. 内容不够丰富，无法体现产品完整度与技术能力。
4. 需要生成技术效果图，不能只放软件截图。
5. 需要先分析真实原因、用户场景和隐藏需求，再实施下一版。
6. 最终方案必须同时列出“用户提出的需求”和“分析后补充的需求”。

## 2. 问题的真实原因

表面问题是“不好看”，根因是仓库角色没有定义清楚。

`liangzai` 不是普通开源库，也不是单纯软件下载页。它同时承担四个任务：

1. **产品入口**：让摄影师快速理解云享传靓仔是什么。
2. **技术背书**：让开发者相信产品不是套壳或概念图。
3. **开源连接**：把 `cube-kit`、`plugin-sdk` 等真实开源零件连接起来。
4. **商业转化**：引导下载、私有化、二次开发和商务咨询。

当前 README 把四类信息平铺在一起，结果是：

- 第一屏像普通项目说明，不像成熟商业软件的发布页。
- 大量截图规格一致，读者看到的是“功能清单”，不是产品叙事。
- Mermaid 只有五个方框，无法形成技术可信度。
- 技术能力、产品能力、开源范围和商业范围没有形成清晰层级。
- 页面缺少可引用、可传播的核心技术视觉资产。

因此，下一版不是“把截图排得更整齐”，而是一次 **信息架构 + 品牌视觉 + 技术叙事的整体重构**。

## 3. 当前版本的具体问题

### 3.1 第一屏没有主视觉

现在是图标、标题、四个 badge、原始截图。元素都有，但没有被合成为一个统一画面，缺少：

- 产品定位；
- 关键差异；
- 真实界面；
- 本机计算 / 可编辑 AI 的技术暗示；
- 明确的下一步动作。

### 3.2 截图数量多，但信息增量低

八张截图按 2×4 表格排列：

- 每张图在 GitHub 内容宽度下太小，界面文字不可读；
- 每一块规格相同，没有主次；
- 连续表格造成视觉疲劳；
- 截图证明“有这个功能”，但没有解释“为什么技术上值得相信”。

### 3.3 技术内容缺少证据层

当前技术部分主要是一张简单流程图和开闭源表。缺少：

- 本机处理与网络边界；
- AI 输出可编辑参数的工作方式；
- 人脸、蒙版、色彩、渲染的协同关系；
- 预览与导出的双路径；
- 开源组件在完整产品中的实际位置；
- 可复核的性能或兼容性证据。

### 3.4 产品文案与正式状态存在风险

以下内容必须以当前 GA 版本为准，不能按开发树或占位 UI 宣传：

- `AI工具箱`、`选片交付` 当前仍是 `disabled: true`，不得作为已开放能力营销；
- 截图中的灰色入口不能被解释成可用功能；
- README、正式更新接口和官网版本信息目前不完全同步；
- 未经正式 benchmark 证明，不写“端侧小于 80ms”等精确性能数字；
- 规划中、开发树已落地、正式版已发布必须明确区分。

### 3.5 “开源连接仓”身份不够突出

读者必须在首屏后很快知道：

- 本仓库是产品技术总览，不是完整软件源码；
- 文档与展示资产采用 CC BY 4.0；
- 真正 MIT 开源的是哪些组件；
- 闭源的是哪些核心资产；
- 为什么这种边界合理，而不是“假开源”。

## 5. 分析后补充的隐藏需求

### P0：必须补充

1. **真实性门禁**  
   只展示当前正式版本已开放能力；开发中能力必须标注。

2. **跨入口一致性**  
   GitHub、官网、更新接口、版本台账的版本与下载地址必须一致。

3. **开发者可信度**  
   首屏不能只推下载，必须尽快展示真实开源仓、安装命令和在线试跑。

4. **知识产权边界**  
   技术图只解释架构，不公开引擎实现、模型权重、风格配方或安全细节。

5. **素材隐私检查**  
   截图中的手机号、项目名、客户照片、账号信息必须确认可公开或打码。

6. **GitHub 媒介适配**  
   GitHub README 无自定义 CSS，设计必须主要通过预渲染视觉资产实现。

### P1：显著提升专业度

1. 建立统一的 README 视觉系统，而不是每张图各自设计。
2. 技术图保留可编辑源文件，后续版本可维护。
3. 只保留一个有叙事意义的 GIF，避免页面像功能轮播广告。
4. 关键图在手机端缩小时仍可读。
5. 图片总重量受控，避免 GitHub 首屏加载过慢。
6. 增加英文一句话定位和英文关键词，但不复制一份冗长英文全文。

### P2：增长与维护

1. 增加 GitHub social preview 封面。
2. README 与 `cube-kit` / `plugin-sdk` 双向内链。
3. 提供可引用的技术图，供掘金、V2EX、官网文章复用。
4. 后续通过脚本或固定数据源更新版本状态，减少手改。
5. 公开 benchmark 前先建立可重复测试方法与环境说明。

## 6. 设计定位

### 改造类型

`Redesign · Overhaul`

保留：

- 产品名称、Logo / 吉祥物、真实界面截图；
- 官网薄荷绿；
- 本机出片、AI 可编辑、开源零件 / 闭源核心；
- 下载、开源仓、私有化三条路径。

改善：

- 第一屏叙事；
- 信息层级；
- 技术可信度；
- 图文节奏；
- 开源连接关系；
- 移动端可读性。

移除：

- 大量重复规格截图；
- 装饰性 badge 堆叠；
- 无证据精确性能数字；
- 未正式开放功能的营销描述；
- 过于口语化、降低专业感的表述。

### 推荐视觉语言

**专业影像工作台 × 开发者技术发布页**

参考方向：

- Capture One / DaVinci Resolve 的专业影像工具感；
- Linear / Raycast 的克制产品发布感；
- Pentagram 的信息架构与版式纪律。

不是：

- 紫蓝渐变的通用 AI 网站；
- 霓虹电路板和机器人头像；
- 满屏圆角卡片；
- 大量 emoji；
- “黑科技”式虚假数据。

### 设计校准

- Visual Variance：6 / 10  
  保持稳定阅读主轴，用 2–3 个非对称技术视觉制造记忆点。
- Motion Intensity：2 / 10  
  README 以静态为主，仅保留一个真实功能巡礼 GIF。
- Information Density：7 / 10  
  内容丰富，但通过总览图、折叠区和证据卡分层。
- Asset Dependence：9 / 10  
  数字产品必须依赖真实 UI、真实图标和真实效果。
- Brand Fidelity：8 / 10  
  保留薄荷绿与真实产品，但提升排版与技术表达。

## 9. 技术实现方案

### 9.1 为什么不直接在 README 里“写设计”

GitHub README 会过滤 CSS 和脚本，自定义字体、复杂布局、玻璃效果都不可靠。因此：

- README 负责语义、链接、代码和可访问文本；
- 视觉设计主要由预渲染图片承载；
- 技术图必须保留源文件，不能只留下不可编辑 PNG。

### 9.2 文件结构

```text
docs/readme/
├── source/
│   ├── design-tokens.json
│   └── render_v0.py
├── rendered/
│   ├── hero-workstation.webp
│   ├── local-first-architecture.webp
│   ├── editable-ai-pipeline.webp
│   ├── multi-model-orchestration.webp
│   ├── open-core-map.webp
│   ├── portrait-proof.webp
│   ├── mask-proof.webp
│   ├── image-tools-proof.webp
│   ├── product-tour-poster.webp
│   └── social-preview.png
├── media/
│   ├── product-tour-720p.mp4
│   └── product-tour-frame.jpg
└── README.md
```

### 9.3 设计令牌

- 背景：暖黑 / 石墨黑，不直接照搬 GitHub `#0D1117`
- 主字：接近白
- 次字：灰蓝
- 主强调：官网薄荷绿 `#3DD6A5`
- 辅助强调：天青，只用于技术路径或交互状态
- 圆角：8 / 12 / 20 三档，有明确语义
- 间距：8pt 系统
- 图中文字：在 1600px 画布上不小于 28px
- 单图颜色：品牌色 + 中性色，最多一个辅助色

### 9.4 图片制作方式

1. 使用真实 UI 截图作为唯一产品界面来源。
2. 使用 Python / Pillow 源脚本生成技术图，确保对齐、文字和路径可控。
3. 统一渲染为 WebP / PNG，保证 GitHub 显示一致。
4. 不使用生成式 AI 重画产品 UI。
5. 如需装饰纹理，只生成非身份关键的背景材质，且不得抢主体。
6. 所有图保留可编辑源文件。

### 9.5 GitHub 适配

- 主图宽 1600px，适配 Retina 和 GitHub 内容宽度；
- 技术图在 390px 手机宽度下仍能识别标题与主路径；
- 一个 GIF 控制在 3MB 内；
- 首屏图片建议小于 700KB；
- 全 README 图片总量建议小于 8MB；
- 图片提供有意义的 `alt`；
- 不依赖外部图床；
- 不把关键事实只写在图片里。
